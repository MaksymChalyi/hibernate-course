# Фінальний проєкт: Mini Bank API

Стартова точка — робочий API з модуля 11: рахунки, перекази, історія сторінками, Flyway, обробка помилок.
Завдання — довести його до рівня, який не соромно показати на співбесіді.

## Вимоги

### 1. Фільтри історії операцій
`GET /accounts/{id}/transactions` приймає необов'язкові параметри:

| Параметр | Приклад | Значення |
|---|---|---|
| `type` | `DEBIT` | Тип операції, без урахування регістру |
| `from` | `2026-01-01` | Дата за Києвом, включно |
| `to` | `2026-01-31` | Дата за Києвом, включно (весь день) |
| `minAmount`, `maxAmount` | `100`, `5000` | Межі суми, включно |

- Фільтр через Criteria API: умова додається лише для переданих параметрів.
- `total` у відповіді враховує фільтр.
- Некоректне значення будь-якого параметра → 400.
- Кількість SQL-запитів не залежить від кількості операцій (жодного N+1).

### 2. Імпорт виписки
`POST /statements`, тіло — CSV (`Content-Type: text/csv`), формат як у модулі 10:
```
account_number;booking_date;amount;currency;description
UA000001;2026-03-15;-1250.50;UAH;Оренда
```
- Нова таблиця `statement_lines` — окремою міграцією Flyway `V3__...`.
- Batching: `hibernate.jdbc.batch_size`, `flush()` + `clear()` пачками.
- Помилка в будь-якому рядку → 400 з номером рядка, жоден рядок не зберігається.
- Відповідь: `{"rows": 1000, "millis": 350}`.

### 3. Тести на справжньому PostgreSQL
- Скопіюй `TestDatabase` з `m12-testing`: він бере Docker-контейнер, якщо Docker є, інакше локальну схему (тут — `m13_test`).
- Базовий клас: база + сервер на випадковому порту, один раз на запуск тестів.
- Застосунок читає підключення з system properties (`AppConfig`): `minibank.db.url`, `minibank.db.user`, `minibank.db.password`, `minibank.db.schema` — підстав значення з `TestDatabase`.
- Чиста база перед кожним тестом (Flyway `clean` + `migrate`, `cleanDisabled(false)`).
- Мінімум: успішний переказ, 422, 400, паралельні перекази, фільтри історії, імпорт, відкат імпорту, тест на кількість SQL.

### 4. README
Коротко поясни рішення: чому pessimistic lock для переказів, чому DTO замість entity, чому `validate` + Flyway, чому SEQUENCE, де межі поточного рішення.

## Критерії приймання

- [ ] `mvn verify` у цьому модулі проходить (з Docker або з локальним PostgreSQL)
- [ ] Усі вимоги 1–4 виконані
- [ ] Жодна entity не потрапляє в JSON
- [ ] Жодного `hbm2ddl.auto=update`
- [ ] Ти можеш пояснити кожен рядок у `persistence.xml`

## Підказки

- Залежність `testcontainers` у `pom.xml` модуля вже підключена; без Docker вона просто не використовується.
- Для тестів з `mvn` прибери `<skipTests>true</skipTests>` з `pom.xml` модуля.
- Звір свій варіант із `../solution` лише після того, як твої тести стануть зеленими.
