**Що треба пам'ятати:** Persistence Context, flush, `clear()` з модуля 3; `IDENTITY` vs `SEQUENCE` з модуля 2.

# Частина 1. Задача і правило вимірювань

Банк отримує від партнера CSV-виписку на 100 000 рядків:

```
account_number;booking_date;amount;currency;description
UA000042;2026-03-15;-1250.50;UAH;Оренда
...
```

Треба зберегти її в таблицю `statement_lines`.

**Правило:** не оптимізувати навмання. Спочатку виміряти, потім змінити **одну** річ, потім виміряти знову.

```xml
<property name="hibernate.generate_statistics" value="true"/>
```

```java
Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
stats.clear();
// ... операція ...
stats.getPrepareStatementCount();   // скільки JDBC-запитів підготовлено
stats.getEntityInsertCount();       // скільки entity вставлено
```

> У цьому модулі логер SQL у `logback.xml` вимкнено: 100 000 рядків `insert` у консолі сповільнили б імпорт у рази. Для перевірки на малому файлі постав рівень `DEBUG`.

# Частина 2. Чому наївний імпорт поганий

```java
em.getTransaction().begin();
for (String line : lines) {
    em.persist(Csv.parse(line));
}
em.getTransaction().commit();
```

**Проблема 1 — пам'ять.** Кожен `persist` кладе об'єкт у Persistence Context **разом зі знімком** (модуль 3). До `commit` там лежать 100 000 об'єктів і 100 000 копій. Пам'ять росте лінійно з розміром файлу. А перед `commit` flush ще й перевіряє кожен з них на зміни.

**Проблема 2 — мережа.** Без batching кожен `INSERT` — окреме звернення до бази: 100 000 «поїздок» туди-назад.

# Частина 3. JDBC batching

## 3.1. Що це

JDBC уміє відправляти **пакет** однакових запитів за одне звернення:

```java
// чистий JDBC
for (...) {
    ps.setString(1, ...);
    ps.addBatch();            // додати в пакет
}
ps.executeBatch();            // відправити все разом
```

Hibernate робить це сам, якщо увімкнути:

```java
Map.of("hibernate.jdbc.batch_size", "50",
       "hibernate.order_inserts", "true",
       "hibernate.order_updates", "true")
```

- `jdbc.batch_size` — скільки запитів у пакеті. Рекомендовано 10–50; більше дає мало виграшу.
- `order_inserts` — групувати `INSERT` за таблицями. Якщо в транзакції чергуються різні entity (операція, рахунок, операція…), без цього пакет розривається на кожній зміні таблиці.

## 3.2. Чому batching «не працює» з IDENTITY

Після `persist` Hibernate мусить знати id (щоб покласти об'єкт у Persistence Context). З `IDENTITY` id видає лише `INSERT` — тому Hibernate виконує `INSERT` **одразу** на кожен `persist`, по одному. `batch_size` при цьому просто ігнорується.

З `SEQUENCE` і `allocationSize = 50` id відомий заздалегідь — і `INSERT` можна накопичити.

Це найчастіша причина «увімкнув batching, а нічого не змінилося».

# Частина 4. flush() + clear() пачками

```java
if (++rows % batchSize == 0) {
    em.flush();    // відправити накопичені INSERT (одним JDBC-пакетом)
    em.clear();    // звільнити Persistence Context
}
```

| Виклик | Що робить | Без нього |
|---|---|---|
| `flush()` | SQL іде в базу | Накопичуємо все до commit |
| `clear()` | Об'єкти стають detached, GC їх прибирає | Пам'ять росте |

**`clear()` без `flush()` — помилка:** незбережені об'єкти стануть detached, і їхні `INSERT` **ніколи не виконаються**. Дані мовчки загубляться.

`batchSize` у коді має дорівнювати `hibernate.jdbc.batch_size` — тоді кожен flush = рівно один пакет.

## 4.1. Одна транзакція чи кілька

У нашому імпорті вся виписка — **одна** транзакція: або все, або нічого. Альтернатива — `commit` кожні N рядків: менше навантаження на базу (коротші транзакції), але після збою частина даних уже збережена, і повторний запуск мусить уміти продовжити з місця зупинки (наприклад, пропускати вже імпортовані рядки).

# Частина 5. Скільки виходить запитів

На 5 000 рядках, `batch_size = 50`, `allocationSize = 50`:

| Імпортер | Запитів (приблизно) | Чому |
|---|---|---|
| naive (без batching) | 5 000 + ~100 | Кожен `INSERT` окремо + `nextval` на кожні 50 id |
| batch | ~100 + ~100 | 100 пакетів по 50 `INSERT` + 100 `nextval` |

Абсолютний час залежить від машини, тому дивимось на **співвідношення**.

**Перевір себе:**
1. Чому з `IDENTITY` batching не працює?
2. Що станеться, якщо викликати `clear()` без `flush()`?
3. Навіщо `order_inserts`?

## Практика (25 хв)

### Крок 0. Виміряти (3 хв)

Тест «Демо · наївний імпорт» → у консолі рядок `naive rows=5,000 time=... statements=...`. Записати.

### Завдання 1. SEQUENCE (3 хв)

У `StatementLine`:

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "statement_line_seq")
@SequenceGenerator(name = "statement_line_seq", sequenceName = "statement_line_seq", allocationSize = 50)
private Long id;
```

### Завдання 2. Batching (4 хв)

У `Emfs.withBatching`:

```java
return Persistence.createEntityManagerFactory("minibank", Map.of(
        "hibernate.jdbc.batch_size", String.valueOf(batchSize),
        "hibernate.order_inserts", "true",
        "hibernate.order_updates", "true"));
```

`createEntityManagerFactory` з другим аргументом — властивості, які **додаються** до `persistence.xml` або перекривають їх. Зручно, щоб мати дві фабрики з різними налаштуваннями.

### Завдання 3. BatchImporter (10 хв)

```java
@Override
public ImportResult importFile(Path csv) {
    Statistics stats = Emfs.statistics(emf);
    stats.clear();
    long started = System.currentTimeMillis();
    long rows = 0;

    try (EntityManager em = emf.createEntityManager();
         BufferedReader reader = Files.newBufferedReader(csv, StandardCharsets.UTF_8)) {
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();
            reader.readLine();                       // заголовок
            String line;
            while ((line = reader.readLine()) != null) {
                em.persist(Csv.parse(line));
                rows++;
                if (rows % batchSize == 0) {
                    em.flush();
                    em.clear();
                }
            }
            tx.commit();
        } catch (RuntimeException e) {
            if (tx.isActive()) {
                tx.rollback();
            }
            throw e;
        }
    } catch (IOException e) {
        throw new UncheckedIOException(e);
    }
    return new ImportResult("batch", rows, System.currentTimeMillis() - started, stats.getPrepareStatementCount());
}
```

### Вимірювання (5 хв)

1. Тест «1–3 · batch …» → зелений, порівняти рядок `batch ...` з `naive ...`.
2. `Main` (100 000 рядків) з VM option `-Xmx128m`: **Run → Edit Configurations → Modify options → Add VM options**. Наївний імпорт падає з `OutOfMemoryError` або різко сповільнюється через збирач сміття; batch — ні. Це і є критерій завершення: пам'ять batch-імпорту не залежить від розміру файлу.

**Якщо не працює:**

| Що бачиш | Причина |
|---|---|
| batch так само повільний, запитів ~5 000 | Залишився `IDENTITY` або фабрика без `batch_size` |
| У базі менше рядків, ніж у файлі | `clear()` без `flush()` |
| `relation "statement_line_seq" does not exist` у JDBC-тесті | Не зроблено завдання 1 |

# Частина 6. Резерв (30 хв)

## 6.1. StatelessSession (8 хв)

```java
StatelessSession session = emf.unwrap(SessionFactory.class).openStatelessSession();
try {
    Transaction tx = session.beginTransaction();
    for (...) session.insert(entity);    // INSERT одразу (з batching — пакетами)
    tx.commit();
} finally {
    session.close();
}
```

Hibernate **без** Persistence Context: немає кешу, знімків, dirty checking, cascade, lazy loading. Для масової вставки, коли об'єкт після вставки не потрібен, — ідеально.

Чого не вміє: зберегти граф об'єктів через cascade; самостійно знайти змінені поля (лише явний `session.update(obj)`); завантажити lazy-зв'язок.

## 6.2. Чистий JDBC batch (5 хв)

`JdbcBatchImporter` — орієнтир «наскільки швидко взагалі можна». Параметр драйвера `reWriteBatchedInserts=true` склеює пакет в один `INSERT ... VALUES (...), (...), ...`. Якщо Hibernate-імпорт повільніший у рази — шукай проблему в налаштуваннях, а не в Hibernate.

## 6.3. Read-only (5 хв)

```java
em.createQuery("select s from StatementLine s where s.accountNumber = :n", StatementLine.class)
  .setHint("org.hibernate.readOnly", true)
```

Hibernate не робить знімків для dirty checking — менше пам'яті при читанні великих списків. Для entity, що ніколи не змінюються (історичні записи) — `@org.hibernate.annotations.Immutable` над класом.

## 6.4. Second-level cache (6 хв)

Кеш між різними `EntityManager`, спільний для застосунку. Потребує провайдера (Ehcache, Infinispan).

| Підходить | Не підходить |
|---|---|
| Довідники: валюти, країни, тарифи | Баланси, операції |
| Читаються часто, змінюються рідко | Дані, які змінюють в обхід Hibernate |

Неправильно налаштований кеш віддає застарілі дані. Для балансів це неприйнятно. Детально — у додатковому матеріалі Д5.

## 6.5. Індекси і EXPLAIN ANALYZE (6 хв)

Візьми SQL з логу і виконай у pgAdmin:

```sql
explain analyze
select * from m10.statement_lines where account_number = 'UA000042' order by booking_date;
```

`Seq Scan` на великій таблиці — сигнал додати індекс:

```sql
create index idx_statement_lines_account_date on m10.statement_lines (account_number, booking_date);
```

Запусти `explain analyze` ще раз: тепер `Index Scan`. Hibernate сам індекси не створює (крім PK, FK-обмежень і `unique`) — у реальному проєкті вони живуть у міграціях (модуль 11).

## Контрольні питання

1. Чому з `IDENTITY` batching не працює?
   *Hibernate виконує INSERT одразу, щоб отримати id.*
2. Що станеться, якщо викликати `clear()` без `flush()`?
   *Незбережені об'єкти стануть detached, їхні INSERT не виконаються.*
3. Навіщо `order_inserts`?
   *Щоб пакети не розривались при чергуванні різних entity.*
4. Чим `StatelessSession` відрізняється від `EntityManager`?
   *Немає Persistence Context: ні кешу, ні dirty checking, ні cascade.*
5. Чому second-level cache небезпечний для балансів?
   *Можна прочитати застарілий баланс.*
