## Розбір домашнього завдання (10 хв)

Зарплатний рахунок: тисячі списань одночасно з **одного** рядка. Optimistic дасть лавину конфліктів і повторів. Pessimistic вишикує їх у чергу — передбачувано, але повільно. Справжнє рішення змінює модель: один пакетний переказ (bulk) замість тисяч окремих або окремий технічний рахунок на кожну партію виплат. Добре, якщо учень дійде до думки, що блокування не єдиний інструмент.

## Теорія (25 хв)

### 1. Задача (2 хв)

Банк отримує CSV-виписку на 100 000 рядків і має зберегти її в таблицю `statement_lines`.

```
account_number;booking_date;amount;currency;description
UA000042;2026-03-15;-1250.50;UAH;Оренда
```

### 2. Чому наївний імпорт поганий (6 хв)

```java
em.getTransaction().begin();
for (String line : lines) {
    em.persist(Csv.parse(line));
}
em.getTransaction().commit();
```

Дві проблеми:

1. **Пам'ять.** Кожен об'єкт лишається в Persistence Context разом зі знімком для dirty checking — до самого commit. 100 000 entity × 2 копії. Під час flush Hibernate ще й перевіряє кожну.
2. **Мережа.** Без batching кожен INSERT — окремий запит до бази: 100 000 round-trip.

### 3. JDBC batching (6 хв)

```java
Map.of("hibernate.jdbc.batch_size", "50",
       "hibernate.order_inserts", "true",
       "hibernate.order_updates", "true")
```

Hibernate накопичує однакові INSERT і відправляє пачками по 50 через `PreparedStatement.addBatch()` / `executeBatch()`. Рекомендований розмір — 10–50; більші пачки дають мало виграшу.

`order_inserts` — групує INSERT за таблицями. Без нього, якщо в транзакції чергуються різні entity (операція, рахунок, операція…), пачка розривається на кожній зміні таблиці.

**Batching не працює з `IDENTITY`** (модуль 2): Hibernate мусить виконати INSERT одразу, щоб дізнатися id. Тому в starter `StatementLine` спершу використовує `IDENTITY` — і перший висновок практики: налаштування є, а пачок немає.

### 4. `flush()` + `clear()` пачками (6 хв)

```java
if (++rows % batchSize == 0) {
    em.flush();   // відправити накопичені INSERT (одним batch)
    em.clear();   // звільнити Persistence Context
}
```

- `flush` без `clear` — SQL пішов, але об'єкти лишаються в пам'яті.
- `clear` без `flush` — **накопичені зміни втрачено**: об'єкти більше не managed, INSERT для них не буде.
- `batchSize` у коді = `hibernate.jdbc.batch_size`.

Одна транзакція на весь файл: або імпортовано все, або нічого. Альтернатива — commit кожні N рядків: менше навантаження на базу, але після збою частина даних уже збережена, і повторний запуск мусить уміти продовжити.

### 5. Як вимірювати (5 хв)

```xml
<property name="hibernate.generate_statistics" value="true"/>
```

```java
Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
stats.clear();
// ... операція ...
stats.getPrepareStatementCount();   // скільки JDBC-запитів підготовлено
stats.getEntityInsertCount();       // скільки entity вставлено
```

Не оптимізуй навмання: спочатку виміряй, потім змінюй одну річ, потім знову виміряй.

## Резерв (30 хв)

### `StatelessSession` (8 хв)

```java
StatelessSession session = emf.unwrap(SessionFactory.class).openStatelessSession();
try {
    Transaction tx = session.beginTransaction();
    for (...) session.insert(entity);    // INSERT одразу
    tx.commit();
} finally {
    session.close();
}
```

Hibernate без Persistence Context: немає first-level cache, dirty checking, cascade, lazy loading. Для імпорту, де об'єкт після вставки не потрібен, — ідеально. Чого він не вміє — зберегти граф об'єктів через cascade або знайти зміни сам.

### Чистий JDBC batch (5 хв)

`JdbcBatchImporter` — орієнтир «наскільки швидко взагалі можна». Параметр драйвера `reWriteBatchedInserts=true` склеює пачку в один `INSERT ... VALUES (...), (...), ...`. Якщо Hibernate-імпорт повільніший у рази — шукай проблему в налаштуваннях, а не в Hibernate.

### Read-only запити (5 хв)

```java
em.createQuery("select s from StatementLine s where s.accountNumber = :n", StatementLine.class)
  .setHint("org.hibernate.readOnly", true)
```

Hibernate не робить знімків для dirty checking — менше пам'яті при читанні великих списків. Для entity, які ніколи не змінюються (довідник валют, історичні записи), — `@org.hibernate.annotations.Immutable` на класі.

### Second-level cache (6 хв)

Кеш між `EntityManager`, спільний для всього застосунку. Потребує провайдера (JCache + Ehcache, Infinispan).

| Підходить | Не підходить |
|---|---|
| Довідники: валюти, країни, тарифи | Баланси, операції — часто змінюються |
| Читається часто, змінюється рідко | Дані, які змінює інший сервіс в обхід Hibernate |

Неправильно налаштований кеш віддає застарілі дані. Для балансів у банку це неприйнятно. Вмикати лише після вимірювання і точково.

### Індекси і `EXPLAIN ANALYZE` (6 хв)

Візьми SQL з логу Hibernate і виконай у `psql`:

```sql
explain analyze
select * from statement_lines where account_number = 'UA000042' order by booking_date;
```

`Seq Scan` на великій таблиці — сигнал додати індекс:

```sql
create index idx_statement_lines_account_date on statement_lines (account_number, booking_date);
```

Hibernate не створює індекси сам (крім PK, FK-обмежень і `unique`). Індекси — у міграціях (модуль 11).

## Контрольні питання

1. Чому `IDENTITY` вимикає batching?
   *Hibernate мусить виконати INSERT одразу після `persist`, щоб отримати id.*
2. Що станеться, якщо викликати `clear()` без `flush()`?
   *Незбережені об'єкти перестануть бути managed, їхні INSERT не виконаються.*
3. Навіщо `order_inserts`?
   *Групує INSERT однієї таблиці, щоб пачки не розривалися при чергуванні entity.*
4. Чим `StatelessSession` відрізняється від `EntityManager`?
   *Немає Persistence Context: ні кешу, ні dirty checking, ні cascade.*
5. Чому second-level cache небезпечний для балансів?
   *Можна прочитати застарілий баланс.*
