## Захист проєкту (30 хв)

### Демонстрація (10 хв)

Учень запускає `mvn verify` (на екрані зелені тести) і показує через `curl`:

```bash
curl http://localhost:8080/accounts/1
curl "http://localhost:8080/accounts/1/transactions?type=DEBIT&from=2026-01-01&to=2026-12-31&size=5"
curl -X POST http://localhost:8080/transfers -H "Content-Type: application/json" \
     -d '{"fromAccountId":3,"toAccountId":1,"amount":100000}'     # 422
curl -X POST http://localhost:8080/statements -H "Content-Type: text/csv" --data-binary @statement.csv
```

### Питання по коду (20 хв)

Відкривай файли учня і питай конкретно:

| Що відкрити | Питання |
|---|---|
| `TransferService` | Чому блокуєш у порядку id? Що буде, якщо прибрати `Math.min`? |
| `Account` | Навіщо `@Version`, якщо є pessimistic lock? |
| `AccountService.history` | Скільки SQL виконає цей метод? Покажи в лозі |
| `StatementImportService` | Що буде, якщо прибрати `em.clear()`? А `em.flush()`? |
| `persistence.xml` | Поясни кожен рядок |
| `V1__schema.sql` | Чому `increment by 50`? Що буде, якщо поставити 1? |
| `AccountDto` | Чому не повертаєш `Account`? |
| Тести | Покажи тест, який зламається, якщо хтось додасть N+1 |

Якщо учень не може пояснити рядок у своєму коді — це сигнал повернутися до відповідного модуля, а не провал.

## Mock-співбесіда (30 хв)

Формат: питання → відповідь учня без підказок → коротке уточнення («а що, якщо…»). Відповіді нижче — орієнтир для викладача, не для зачитування.

### 1. Життєвий цикл entity і Persistence Context

**Очікувана відповідь:** чотири стани — transient, managed, detached, removed. Persistence Context — мапа managed-об'єктів у `EntityManager` зі знімками стану: дає first-level cache, ідентичність об'єктів і dirty checking.

**Уточнення:** «Ти змінив поле в об'єкті з `find` і не викликав `save`. Що буде?» → UPDATE при flush.

### 2. N+1: як знайти і виправити

**Очікувана відповідь:** 1 запит на список + по запиту на кожен lazy-зв'язок. Знайти — однакові SELECT у лозі, лічильник Statistics у тесті. Виправити — `JOIN FETCH`, entity graph, DTO-проєкція; `default_batch_fetch_size` як страховка.

**Уточнення:** «Чому не зробити зв'язок EAGER?» → вантажиться завжди, і в JPQL однаково дає окремі запити.

### 3. `LazyInitializationException`

**Очікувана відповідь:** звернення до незавантаженого lazy-зв'язку після закриття `EntityManager`. Рішення — завантажити потрібне в запиті або повернути DTO. Не рішення — EAGER, Open Session in View, `enable_lazy_load_no_trans`.

### 4. `merge` vs `persist`

**Очікувана відповідь:** `persist` робить новий об'єкт managed. `merge` копіює стан detached-об'єкта в managed-копію і повертає її; працювати треба з результатом.

**Уточнення:** «Що буде, якщо змінити переданий у `merge` об'єкт після виклику?» → зміна не збережеться.

### 5. Optimistic vs pessimistic locking

**Очікувана відповідь:** optimistic — `@Version`, конфлікт при записі, повтор; для рідкісних конфліктів і довгих операцій. Pessimistic — `SELECT FOR UPDATE`, очікування; для частих конфліктів і коротких транзакцій. Ризик pessimistic — deadlock, рішення — порядок блокувань.

### 6. Чим Hibernate відрізняється від JDBC і коли JDBC кращий

**Очікувана відповідь:** Hibernate прибирає ручний mapping, керує графом об'єктів, dirty checking, кешем. JDBC кращий для масових операцій, складної аналітики, коли потрібен повний контроль над SQL. Можна поєднувати в одному проєкті.

### 7. `IDENTITY` vs `SEQUENCE`

**Очікувана відповідь:** `IDENTITY` — id з INSERT, тому Hibernate вставляє одразу і batching вимкнено. `SEQUENCE` з `allocationSize` — id відомий до INSERT, одне звернення до послідовності на пачку id, batching працює.

### 8. Owning side зв'язку

**Очікувана відповідь:** сторона, що керує foreign key; для `@ManyToOne` — завжди вона. Inverse side позначена `mappedBy` і на SQL не впливає. Тому helper-методи встановлюють обидві сторони.

### Оцінювання

| Відповідей без підказок | Результат |
|---|---|
| 7–8 | Готовий до Hibernate-питань на позиції Junior/Middle |
| 6 | Курс завершено |
| 4–5 | Повторити модулі з помилками, повторна співбесіда через тиждень |
| < 4 | Повторити модулі 3, 5, 6 |

## Що далі: міст до Spring

| Зараз робимо вручну | У Spring |
|---|---|
| `EntityManagerFactory` у `ServletContextListener` | Автоконфігурація Spring Boot |
| `Tx.inTransaction(...)` | `@Transactional` |
| Сервіс з `EntityManagerFactory` | Репозиторій `JpaRepository` |
| JPQL у сервісі | Derived queries, `@Query` |
| `page * size` вручну | `Pageable`, `Page` |
| Servlet + Jackson + `writeError` | `@RestController` + `@ControllerAdvice` |
| `AppContext` | IoC-контейнер |

Механізми під капотом — Persistence Context, flush, lazy loading, блокування — лишаються тими самими. Саме тому курс Hibernate ішов першим.
