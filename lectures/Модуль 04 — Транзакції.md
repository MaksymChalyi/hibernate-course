## Теорія (25 хв)

### 1. Навіщо транзакція в переказі (5 хв)

Переказ 250 грн з рахунку A на рахунок B — це **чотири** зміни:

1. Баланс A −250
2. Запис операції DEBIT для A
3. Баланс B +250
4. Запис операції CREDIT для B

Якщо застосунок впаде між кроками 2 і 3, гроші зникнуть. Транзакція гарантує: або всі чотири зміни, або жодна.

**ACID** на цьому прикладі:

| | Що означає для переказу |
|---|---|
| **A**tomicity | Або 4 зміни, або 0 |
| **C**onsistency | Баланс не стає від'ємним, сума грошей у системі не змінюється |
| **I**solation | Паралельний переказ не бачить «половини» нашого |
| **D**urability | Після commit переказ не зникне навіть після вимкнення сервера |

### 2. `EntityTransaction` і порівняння з JDBC (7 хв)

| JDBC | JPA |
|---|---|
| `connection.setAutoCommit(false)` | `em.getTransaction().begin()` |
| `connection.commit()` | `tx.commit()` |
| `connection.rollback()` | `tx.rollback()` |

Шаблон, який повторюватиметься в кожному методі запису:

```java
try (EntityManager em = emf.createEntityManager()) {
    EntityTransaction tx = em.getTransaction();
    try {
        tx.begin();
        // ... робота ...
        tx.commit();
    } catch (RuntimeException e) {
        if (tx.isActive()) {
            tx.rollback();
        }
        throw e;            // не ковтати!
    }
}
```

Три типові помилки в цьому шаблоні:

- **проковтнути виняток** (`catch` без `throw`) — клієнт думає, що переказ пройшов;
- **rollback без перевірки `isActive()`** — якщо `commit` уже впав, rollback кине ще один виняток і сховає першопричину;
- **ловити лише `PersistenceException`** — бізнес-помилка (`InsufficientFundsException`) не відкотить транзакцію.

### 3. Де перевіряти бізнес-правила (5 хв)

```java
public class Account {
    public void debit(BigDecimal amount) {
        if (balance.compareTo(amount) < 0) {
            throw new InsufficientFundsException(number, balance, amount);
        }
        balance = balance.subtract(amount);
    }
}
```

Правило «не піти в мінус» — в entity, а не в сервісі. Хоч би хто списував гроші (переказ, комісія, імпорт), перевірка спрацює. Сервіс координує: знайти рахунки, викликати методи, зберегти операції, керувати транзакцією.

### 4. Одна бізнес-операція — одна транзакція (5 хв)

❌ Погано: кожен крок у своїй транзакції.

```java
accountDao.debit(fromId, amount);     // commit
accountDao.credit(toId, amount);      // впало → гроші списано, але не зараховано
```

✅ Добре: межа транзакції — бізнес-операція «переказ», а не окремий SQL.

Інша крайність — транзакція на весь HTTP-запит з довгими зовнішніми викликами всередині. Транзакція тримає з'єднання і блокування; чим вона коротша, тим краще. Виклик іншого сервісу, відправку email, генерацію PDF робимо **поза** транзакцією.

### 5. Бізнес-винятки (3 хв)

```java
public abstract class BankException extends RuntimeException { ... }
public class InsufficientFundsException extends BankException { ... }
```

Чому `RuntimeException`: помилку не можна виправити на місці виклику, її треба донести до користувача. Окремі класи потрібні, щоб у модулі 11 перетворити їх на різні HTTP-статуси (404, 422).

```java
            em.persist(Transaction.debit(from.getId(), amount, "Переказ на " + to.getNumber()));

            afterDebit.run();    // тут тест імітує збій

            to.credit(amount);
            em.persist(Transaction.credit(to.getId(), amount, "Переказ з " + from.getNumber()));

            tx.commit();
        } catch (RuntimeException e) {
            if (tx.isActive()) tx.rollback();
            throw e;
        }
    }
}
```

`afterDebit` — гачок для тесту: `failureAfterDebitRollsBackEverything` кидає в ньому виняток. Після цього баланси мають бути початковими, а записів `Transaction` — нуль.

Покажи в лозі: при збої **немає** жодного UPDATE чи INSERT — до flush справа не дійшла. Потім додай `em.flush()` перед `afterDebit.run()` і запусти знову: тепер UPDATE і INSERT у лозі є, але тест однаково зелений. Це доводить, що відкат робить база, а не «Hibernate просто не встиг».

## Резерв (30 хв)

### Рівні ізоляції в PostgreSQL (12 хв)

| Рівень | Що бачить транзакція | PostgreSQL |
|---|---|---|
| Read Uncommitted | Чужі незакомічені зміни | Працює як Read Committed |
| **Read Committed** | Лише закомічені дані на момент **кожного запиту** | **За замовчуванням** |
| Repeatable Read | Знімок на момент першого запиту транзакції | Конфлікт при оновленні → помилка серіалізації |
| Serializable | Як послідовне виконання | Найсуворіший, більше відкатів |

Що важливо для переказів: на Read Committed два паралельні перекази з одного рахунку можуть прочитати той самий баланс і обидва його перезаписати — **lost update**. Тести цього модуля однопотокові, тому проблему не видно. Розв'язуємо в модулі 9 блокуваннями, а не підвищенням рівня ізоляції.

### Persistence Context після rollback (6 хв)

Після rollback об'єкти в пам'яті **не** повертаються до старих значень: `from.getBalance()` усе ще показує списану суму. JPA вважає такий Persistence Context непридатним. Правило: після rollback закрити `EntityManager` і почати з нового. У нашому шаблоні це відбувається автоматично через try-with-resources.

```java
public static <T> T inTransaction(EntityManagerFactory emf, Function<EntityManager, T> work) {
    try (EntityManager em = emf.createEntityManager()) {
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();
            T result = work.apply(em);
            tx.commit();
            return result;
        } catch (RuntimeException e) {
            if (tx.isActive()) tx.rollback();
            throw e;
        }
    }
}

// використання
Long id = Tx.inTransaction(emf, em -> {
    Account account = new Account("UA100", CurrencyCode.EUR, BigDecimal.ONE);
    em.persist(account);
    return account.getId();
});
```

Це ручна версія `@Transactional` зі Spring. Коли учень дійде до Spring, варто повернутися до цього класу і порівняти.

## Контрольні питання

1. Чому переказ має бути однією транзакцією, а не двома?
   *Збій між списанням і зарахуванням інакше залишить гроші списаними.*
2. Навіщо `if (tx.isActive())` перед rollback?
   *Якщо `commit` уже впав і транзакція неактивна, rollback кине новий виняток і сховає першопричину.*
3. Чому перевірка балансу в `Account.debit`, а не в сервісі?
   *Правило діє для будь-якого коду, що списує гроші.*
4. Що станеться з об'єктами в пам'яті після rollback?
   *Вони зберігають змінені значення; `EntityManager` треба закрити.*
5. Який рівень ізоляції в PostgreSQL за замовчуванням і яку проблему він не вирішує?
   *Read Committed; не захищає від lost update при read-modify-write.*

## Типові помилки

| Помилка | Наслідок |
|---|---|
| `catch (Exception e) { log.error(...); }` без `throw` | Клієнт отримує «успіх», а переказу немає |
| Окремі транзакції на debit і credit | Гроші зникають при збої |
| `catch (PersistenceException)` замість `RuntimeException` | Бізнес-помилка не відкочує транзакцію |
| Робота з `EntityManager` після rollback | Непередбачувані дані в пам'яті |
