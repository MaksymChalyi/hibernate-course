# Частина 1. Що таке транзакція

## 1.1. Задача: переказ 250 грн

Ольга переказує Івану 250 грн. У базі це **чотири** зміни:

```
1. UPDATE accounts SET balance = balance - 250 WHERE id = <рахунок Ольги>
2. INSERT INTO transactions (... 'DEBIT', 250, 'Переказ на UA002' ...)
3. UPDATE accounts SET balance = balance + 250 WHERE id = <рахунок Івана>
4. INSERT INTO transactions (... 'CREDIT', 250, 'Переказ з UA001' ...)
```

Що, як сервер вимкнеться між кроками 2 і 3? У Ольги гроші списані, Іван нічого не отримав. 250 грн зникли.

**Транзакція** — група операцій, яку база виконує **як одну**: або всі зміни фіксуються, або жодна.

```
begin
  крок 1  ✔
  крок 2  ✔
  крок 3  ✘ збій
rollback  → кроки 1 і 2 скасовано, база така, ніби нічого не було
```

## 1.2. ACID на прикладі переказу

| Літера | Назва | Що означає для переказу |
|---|---|---|
| **A** | Atomicity — атомарність | Або 4 зміни, або 0. «Половини переказу» не буває |
| **C** | Consistency — узгодженість | Правила даних не порушуються: баланс не стає від'ємним, сума грошей у системі не змінюється |
| **I** | Isolation — ізольованість | Інший запит не бачить «половину» нашого переказу, поки ми не закомітили |
| **D** | Durability — довговічність | Після `commit` переказ не зникне, навіть якщо сервер вимкнеться через секунду |

## 1.3. Транзакція — це про базу, не про Java

Важливо розуміти: транзакцію виконує **PostgreSQL**, а не Hibernate. Hibernate лише каже базі «почни», «зафіксуй», «скасуй». Саме тому rollback скасовує навіть SQL, який уже дійшов до бази.

**Перевір себе:**
1. Скільки змін у базі робить один переказ?
2. Що означає «A» в ACID на прикладі переказу?

# Частина 2. Транзакції в коді

## 2.1. JDBC і JPA — те саме різними словами

| JDBC | JPA / Hibernate |
|---|---|
| `connection.setAutoCommit(false)` | `em.getTransaction().begin()` |
| `connection.commit()` | `tx.commit()` |
| `connection.rollback()` | `tx.rollback()` |

## 2.2. Шаблон, розібраний по рядках

```java
try (EntityManager em = emf.createEntityManager()) {     // (1)
    EntityTransaction tx = em.getTransaction();
    try {
        tx.begin();                                      // (2)
        // ... робота ...                                // (3)
        tx.commit();                                     // (4)
    } catch (RuntimeException e) {                       // (5)
        if (tx.isActive()) {                             // (6)
            tx.rollback();                               // (7)
        }
        throw e;                                         // (8)
    }
}                                                        // (9)
```

1. Відкриваємо `EntityManager`. try-with-resources закриє його в кінці за будь-яких умов.
2. Починаємо транзакцію.
3. Робота: `find`, `persist`, зміна полів.
4. `commit`: Hibernate робить flush (відправляє весь накопичений SQL) і фіксує транзакцію.
5. Ловимо **будь-який** `RuntimeException` — і помилку бази, і наш `InsufficientFundsException`.
6. Транзакція ще активна? Якщо впав сам `commit`, вона вже неактивна, і `rollback` кинув би новий виняток, який сховав би справжню причину.
7. Скасовуємо все, що зроблено.
8. Кидаємо **той самий** виняток далі: той, хто викликав переказ, має дізнатися, що він не вдався.
9. `EntityManager` закрито.

## 2.3. Три типові помилки

```java
// Помилка 1: проковтнули виняток
} catch (RuntimeException e) {
    tx.rollback();
    log.error("Помилка", e);       // без throw — клієнт думає, що переказ пройшов
}

// Помилка 2: ловимо не те
} catch (PersistenceException e) { // наш InsufficientFundsException — не PersistenceException
    tx.rollback();                 // → бізнес-помилка не відкотить транзакцію
    throw e;
}

// Помилка 3: rollback без перевірки
} catch (RuntimeException e) {
    tx.rollback();                 // якщо впав commit — тут новий виняток, оригінальний загублено
    throw e;
}
```

## 2.4. Після rollback об'єкти в пам'яті «брешуть»

Rollback скасовує зміни **в базі**. Об'єкти в Java залишаються такими, якими ми їх зробили:

```java
from.debit(new BigDecimal("250"));   // у пам'яті баланс 750
// ... збій, rollback ...
from.getBalance();                   // 750 — хоча в базі 1000
```

Тому після rollback `EntityManager` закривають і працюють з новим. У нашому шаблоні це відбувається автоматично: `rollback` → `throw` → try-with-resources закриває `EntityManager`.

**Перевір себе:**
1. Навіщо `if (tx.isActive())` перед `rollback`?
2. Чому в `catch` має бути `throw e`?

# Частина 3. Межа транзакції = бізнес-операція

## 3.1. Неправильно: транзакція на кожен крок

```java
accountDao.debit(fromId, amount);     // своя транзакція → commit
accountDao.credit(toId, amount);      // своя транзакція → впало → гроші вже списані
```

Кожен DAO-метод окремо коректний, а разом — ні.

## 3.2. Правильно: транзакція на всю операцію

Межу транзакції визначає **бізнес**: «переказ» — одна операція, отже одна транзакція. Тому транзакцією керує сервіс (`TransferService`), а не окремі методи збереження.

## 3.3. Не робити транзакцію занадто довгою

Інша крайність — тримати транзакцію відкритою під час повільних дій: виклик іншого сервісу, відправка email, генерація PDF. Транзакція тримає з'єднання з базою і блокування рядків (модуль 9). Довга транзакція = інші запити чекають. Правило: **у транзакції лише робота з базою; усе повільне — до або після.**

# Частина 4. Де живуть бізнес-правила

## 4.1. Правило в entity

```java
public class Account {
    public void debit(BigDecimal amount) {
        if (balance.compareTo(amount) < 0) {
            throw new InsufficientFundsException(number, balance, amount);
        }
        balance = balance.subtract(amount);
    }
}
```

Правило «не можна піти в мінус» — у самому рахунку. Хоч би хто списував гроші — переказ, комісія, імпорт (модуль 10) — перевірка спрацює. Якби вона була лише в `TransferService`, наступний розробник, що пише списання комісії, міг би про неї забути.

## 4.2. Сервіс координує

`TransferService` не рахує баланси сам. Він:
1. перевіряє аргументи;
2. знаходить рахунки;
3. викликає `from.debit(...)` і `to.credit(...)`;
4. записує операції;
5. керує транзакцією.

## 4.3. Свої винятки

```java
public abstract class BankException extends RuntimeException { ... }
public class InsufficientFundsException extends BankException { ... }
public class AccountNotFoundException extends BankException { ... }
public class CurrencyMismatchException extends BankException { ... }
```

Чому `RuntimeException`, а не checked: на місці виклику цю помилку не виправити — її треба донести до користувача. Чому окремі класи: у модулі 11 кожен перетвориться на свій HTTP-статус (404, 422).

## 4.4. Чому баланси не треба «зберігати»

```java
Account from = em.find(Account.class, fromId);   // managed
from.debit(amount);                               // лише змінили поле
// em.persist(from) / em.merge(from) — НЕ потрібно
tx.commit();                                      // dirty checking → UPDATE accounts ...
```

Це модуль 3 у дії. А ось записи `Transaction` — нові об'єкти (transient), тому для них `em.persist(...)` потрібен.

## Практика (25 хв)

### Завдання 1. TransferService.transfer

**Файл:** `TransferService.java`. Кроки 1–8 — у коментарі над методом. Нижче — повний розв'язок для викладача.

```java
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    if (amount == null || amount.signum() <= 0) {
        throw new IllegalArgumentException("Сума переказу має бути більшою за нуль");
    }
    if (fromId.equals(toId)) {
        throw new IllegalArgumentException("Не можна переказати кошти на той самий рахунок");
    }

    try (EntityManager em = emf.createEntityManager()) {
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();

            Account from = findAccount(em, fromId);
            Account to = findAccount(em, toId);

            from.debit(amount);
            em.persist(Transaction.debit(from.getId(), amount, "Переказ на " + to.getNumber()));

            afterDebit.run();

            to.credit(amount);
            em.persist(Transaction.credit(to.getId(), amount, "Переказ з " + from.getNumber()));

            tx.commit();
        } catch (RuntimeException e) {
            if (tx.isActive()) {
                tx.rollback();
            }
            throw e;
        }
    }
}

private Account findAccount(EntityManager em, Long id) {
    Account account = em.find(Account.class, id);
    if (account == null) {
        throw new AccountNotFoundException(id);
    }
    return account;
}
```

**Що таке `afterDebit`.** Це «гачок» для тестів: код, який виконується між списанням і зарахуванням. У звичайному житті він порожній. Тест «збій посередині» передає туди `() -> { throw new IllegalStateException(...); }` і перевіряє, що після збою **нічого не змінилося**.

**Перевірка:**
1. Тести «1 · …» зелені.
2. Консоль успішного переказу: 2 `select` (рахунки), 2 `insert` (операції), 2 `update` (баланси). `update` і `insert` з'являються лише при `commit`.
3. Консоль тесту «збій посередині»: лише 2 `select` — до flush справа не дійшла.

### Експеримент (5 хв)

Додай `em.flush();` перед `afterDebit.run()` і запусти «збій посередині» знову. Тепер у консолі є `update` і `insert` — SQL **дійшов до бази**. Тест однаково зелений, бо `rollback` скасовує виконані в транзакції зміни на рівні бази. Це доводить: rollback — справа PostgreSQL, а не «Hibernate не встиг». Поверни код.

# Частина 5. Резерв (30 хв)

## 5.1. Рівні ізоляції PostgreSQL (12 хв)

«I» в ACID має рівні: наскільки сильно транзакції ізольовані одна від одної.

| Рівень | Що бачить транзакція | У PostgreSQL |
|---|---|---|
| Read Uncommitted | Навіть незакомічені зміни інших | Працює як Read Committed |
| **Read Committed** | Лише закомічені дані на момент **кожного запиту** | **За замовчуванням** |
| Repeatable Read | Знімок на момент першого запиту транзакції | Конфлікт оновлення → помилка, треба повторити |
| Serializable | Як ніби транзакції виконувались по черзі | Найсуворіший, найбільше повторів |

Що важливо для нас: на Read Committed **два паралельні перекази з одного рахунку** можуть прочитати той самий баланс 1000, обидва відняти по 10 і обидва записати 990. Одне списання зникне. Це **lost update** («втрачене оновлення»). Тести цього модуля однопотокові, тому проблему не видно. Вирішуємо її в модулі 9 блокуваннями.

## 5.2. Helper Tx (18 хв, завдання 3)

Шаблон транзакції ми написали вже кілька разів. Винесемо його:

```java
public static <T> T inTransaction(EntityManagerFactory emf, Function<EntityManager, T> work) {
    try (EntityManager em = emf.createEntityManager()) {
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();
            T result = work.apply(em);
            tx.commit();
            return result;
        } catch (RuntimeException e) {
            if (tx.isActive()) {
                tx.rollback();
            }
            throw e;
        }
    }
}

public static void runInTransaction(EntityManagerFactory emf, Consumer<EntityManager> work) {
    inTransaction(emf, em -> {
        work.accept(em);
        return null;
    });
}
```

Використання:

```java
Long id = Tx.inTransaction(emf, em -> {
    Account account = new Account("UA100", CurrencyCode.EUR, BigDecimal.ONE);
    em.persist(account);
    return account.getId();
});
```

`Function<EntityManager, T>` — «шматок коду, що отримує `EntityManager` і повертає `T`». Лямбда `em -> { ... }` — і є цей шматок.

Це ручна версія `@Transactional` зі Spring. Коли дійдете до Spring, поверніться до цього класу і порівняйте.

## Словник

| Термін | Простими словами |
|---|---|
| Транзакція | Група змін, які база виконує як одну |
| Commit | Зафіксувати транзакцію |
| Rollback | Скасувати всі зміни транзакції |
| ACID | Чотири гарантії транзакції |
| Рівень ізоляції | Наскільки транзакції «не бачать» одна одну |
| Lost update | Паралельна транзакція перезаписала наші зміни |

## Контрольні питання

1. Чому переказ — одна транзакція, а не дві?
   *Збій між списанням і зарахуванням інакше залишить гроші списаними.*
2. Навіщо `if (tx.isActive())` перед rollback?
   *Якщо впав commit, rollback кинув би новий виняток і сховав причину.*
3. Чому в `catch` обов'язковий `throw e`?
   *Інакше той, хто викликав, вважатиме операцію успішною.*
4. Чому перевірка балансу в `Account.debit`, а не в сервісі?
   *Правило діє для будь-якого коду, що списує гроші.*
5. Чому для балансів не потрібен `persist`/`merge`, а для `Transaction` — потрібен?
   *Рахунки managed (dirty checking), операції — нові об'єкти.*
6. Який рівень ізоляції в PostgreSQL за замовчуванням і що він не вирішує?
   *Read Committed; не захищає від lost update.*
