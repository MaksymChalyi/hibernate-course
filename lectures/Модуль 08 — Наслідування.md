## Теорія (25 хв)

### 1. Задача (3 хв)

Платіж буває картковий (маска картки, торговець) і SEPA (IBAN отримувача, ім'я). Спільне: сума, валюта, статус, рахунок платника. В Java це абстрактний `Payment` і два нащадки. У реляційній базі наслідування немає — його треба емулювати.

### 2. `@MappedSuperclass` — спільні поля без наслідування в базі (5 хв)

```java
@MappedSuperclass
public abstract class BaseEntity {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    @PrePersist protected void onCreate() { createdAt = Instant.now(); updatedAt = createdAt; }
    @PreUpdate  protected void onUpdate() { updatedAt = Instant.now(); }
}
```

- Таблиці `base_entity` немає: поля копіюються в таблицю кожного нащадка.
- Поліморфний запит `select b from BaseEntity b` неможливий — це не entity.
- `@PrePersist`, `@PreUpdate` — lifecycle callbacks: Hibernate викликає їх перед INSERT і UPDATE. `@PreUpdate` спрацьовує лише тоді, коли dirty checking знайшов зміни.

Це не «наслідування в базі», а спосіб не повторювати код. Використовують майже в кожному проєкті.

### 3. `SINGLE_TABLE` (7 хв)

```java
@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type", length = 10)
public abstract class Payment extends BaseEntity { ... }

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    @Column(name = "card_mask", length = 19)   // без nullable = false!
    private String cardMask;
}
```

```
payments
id | payment_type | amount | ... | card_mask           | merchant | beneficiary_iban       | beneficiary_name
1  | CARD         | 450    | ... | 4441 **** **** 1234 | Silpo    | NULL                   | NULL
2  | SEPA         | 1200   | ... | NULL                | NULL     | DE89370400440532013000 | Hans Muller
```

| ✅ | ❌ |
|---|---|
| Будь-який запит — одна таблиця без JOIN | Колонки нащадків nullable: база не гарантує, що в картки є маска |
| Поліморфний запит найшвидший | Таблиця розширюється з кожним новим типом |
| Простий INSERT | Багато NULL |

### 4. `JOINED` (7 хв)

```java
@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class Payment extends BaseEntity { ... }

@Entity
@Table(name = "card_payments")
@PrimaryKeyJoinColumn(name = "payment_id")
public class CardPayment extends Payment {
    @Column(name = "card_mask", nullable = false, length = 19)   // NOT NULL можливий
    private String cardMask;
}
```

```
payments: id, amount, currency, status, payer_account, created_at, updated_at
card_payments: payment_id (PK і FK → payments.id), card_mask, merchant
sepa_payments: payment_id (PK і FK → payments.id), beneficiary_iban, beneficiary_name
```

| ✅ | ❌ |
|---|---|
| Нормалізовано, NOT NULL на полях нащадків | Завантаження нащадка — JOIN двох таблиць |
| Нова таблиця для нового типу | Поліморфний запит — LEFT JOIN усіх таблиць |
| | INSERT нащадка — два INSERT |

### 5. Як обирати (3 хв)

| Ситуація | Стратегія |
|---|---|
| Мало специфічних полів, часті поліморфні запити («усі платежі клієнта») | `SINGLE_TABLE` |
| Багато специфічних полів, важлива цілісність, запити переважно до конкретного типу | `JOINED` |
| Типи майже ніколи не запитують разом | Окремі entity без наслідування |

Для платежів у банку часто обирають `SINGLE_TABLE`: «історія платежів» — поліморфний запит, специфічних полів небагато. Але обидві відповіді прийнятні, якщо учень обґрунтовує вибір.

## Резерв (30 хв)

### `TABLE_PER_CLASS` (10 хв)

```java
@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class Payment extends BaseEntity { ... }   // таблиці немає

@Entity @Table(name = "card_payments") public class CardPayment extends Payment { ... }
@Entity @Table(name = "sepa_payments") public class SepaPayment extends Payment { ... }
```

Кожен конкретний клас — повна таблиця з усіма полями, включно зі спільними.

- Запит до конкретного типу — одна таблиця без JOIN.
- Поліморфний запит — `UNION ALL` усіх таблиць: повільно і складно для індексів.
- **`IDENTITY` заборонено:** id мають бути унікальні в усій ієрархії, а в кожної таблиці своя identity-колонка. Потрібна спільна послідовність.

Використовують рідко.

### Поліморфні запити і `TYPE()` (8 хв)

```java
select p from Payment p                              -- усі платежі, Hibernate створить потрібні класи
select p from Payment p where type(p) = CardPayment  -- лише карткові
select c from CardPayment c where c.merchant = 'Silpo'  -- запит до нащадка напряму
```

`TYPE()` у `SINGLE_TABLE` — умова на дискримінатор; у `JOINED` — перевірка, у якій таблиці нащадка є рядок.

### Композиція замість наслідування (12 хв)

Наслідування в entity — жорстке рішення: змінити стратегію на живих даних — міграція всієї ієрархії. Альтернатива:

```java
@Entity
public class Payment {
    @Enumerated(EnumType.STRING) private PaymentMethod method;  // CARD, SEPA
    @Embedded private CardDetails card;                          // null для SEPA
    @Embedded private SepaDetails sepa;                          // null для карток
}
```

Структурно це `SINGLE_TABLE`, але без ієрархії класів: поведінка залежить від `method`. Або окремі таблиці деталей з `@OneToOne`.

Коли наслідування доречне: нащадки мають **різну поведінку**, яку зручно виразити поліморфізмом. Коли лише різні поля — композиція простіша.

## Контрольні питання

1. Чим `@MappedSuperclass` відрізняється від `@Entity` з `@Inheritance`?
   *`@MappedSuperclass` лише копіює поля в таблиці нащадків; поліморфних запитів немає.*
2. Чому в `SINGLE_TABLE` поля нащадків nullable?
   *Рядки інших типів у тій самій таблиці не мають цих значень.*
3. Скільки INSERT для `CardPayment` у `JOINED`?
   *Два: у `payments` і `card_payments`.*
4. Чому `TABLE_PER_CLASS` не працює з `IDENTITY`?
   *Id мають бути унікальні в усій ієрархії, а identity-колонки окремі в кожній таблиці.*
5. Яку стратегію обрати для «історії всіх платежів клієнта»?
   *`SINGLE_TABLE`: поліморфний запит без JOIN.*
