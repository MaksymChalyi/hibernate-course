# Модуль 8. Наслідування

**Що вмітимеш після модуля:**
- виносити спільні поля entity в батьківський клас;
- зберігати ієрархію класів у реляційній базі трьома способами;
- обирати спосіб і пояснювати його ціну;
- використовувати lifecycle callbacks (`@PrePersist`, `@PreUpdate`).

**Код:** `m08-inheritance/starter` → `m08-inheritance/solution`

**Що треба пам'ятати:** `extends` і поліморфізм у Java; `@Column` і `@Table` з модуля 2.

# Частина 1. Задача

Платежі бувають різні:

| | Картковий | SEPA-переказ |
|---|---|---|
| Спільне | сума, валюта, статус, рахунок платника | те саме |
| Своє | маска картки, торговець | IBAN отримувача, ім'я отримувача |

У Java це природна ієрархія:

```java
public abstract class Payment { BigDecimal amount; CurrencyCode currency; ... }
public class CardPayment extends Payment { String cardMask; String merchant; }
public class SepaPayment extends Payment { String beneficiaryIban; String beneficiaryName; }
```

І природний поліморфний запит: «усі платежі клієнта» — `List<Payment>`, де кожен елемент — справжній `CardPayment` або `SepaPayment`.

**Проблема:** у реляційній базі наслідування немає. Таблиця — це просто рядки й колонки. Hibernate пропонує три способи емулювати ієрархію.

# Частина 2. @MappedSuperclass — спільні поля без наслідування в базі

Спочатку простіше: майже в кожного entity є `id`, `created_at`, `updated_at`. Не хочеться повторювати ці поля в кожному класі.

```java
@MappedSuperclass
public abstract class BaseEntity {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE)
    private Long id;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    @PrePersist
    protected void onCreate() {
        createdAt = Instant.now();
        updatedAt = createdAt;
    }

    @PreUpdate
    protected void onUpdate() {
        updatedAt = Instant.now();
    }
}
```

**`@MappedSuperclass`** — це **не** entity:
- таблиці `base_entity` немає;
- поля просто «копіюються» в таблицю кожного нащадка;
- запит `select b from BaseEntity b` неможливий.

Це спосіб не повторювати код, а не «наслідування в базі».

## 2.1. Lifecycle callbacks

| Анотація | Коли Hibernate викликає метод |
|---|---|
| `@PrePersist` | Перед `INSERT` (при `persist`) |
| `@PostPersist` | Після `INSERT` |
| `@PreUpdate` | Перед `UPDATE` — лише якщо dirty checking знайшов зміни |
| `@PostLoad` | Після завантаження з бази |
| `@PreRemove` | Перед `DELETE` |

Зручно для дат створення/зміни, нормалізації даних (email у нижній регістр). Не для бізнес-логіки: callback не можна викликати явно, і він не спрацьовує для bulk update (модуль 7).

# Частина 3. SINGLE_TABLE — уся ієрархія в одній таблиці

```java
@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "payment_type", length = 10)
public abstract class Payment extends BaseEntity { ... }

@Entity
@DiscriminatorValue("CARD")
public class CardPayment extends Payment {
    @Column(name = "card_mask", length = 19)     // без nullable = false!
    private String cardMask;
}

@Entity
@DiscriminatorValue("SEPA")
public class SepaPayment extends Payment { ... }
```

Результат у базі:

```
payments
id │ payment_type │ amount │ currency │ ... │ card_mask           │ merchant │ beneficiary_iban       │ beneficiary_name
───┼──────────────┼────────┼──────────┼─────┼─────────────────────┼──────────┼────────────────────────┼─────────────────
 1 │ CARD         │ 450    │ UAH      │ ... │ 4441 **** **** 1234 │ Silpo    │ NULL                   │ NULL
 2 │ SEPA         │ 1200   │ EUR      │ ... │ NULL                │ NULL     │ DE89370400440532013000 │ Hans Muller
```

**Дискримінатор** (`payment_type`) — колонка-«мітка». Читаючи рядок, Hibernate дивиться на неї і вирішує, об'єкт якого класу створити.

| Плюси | Мінуси |
|---|---|
| Будь-який запит — одна таблиця, без JOIN | Колонки нащадків **мусять бути nullable**: у рядку картки немає IBAN |
| Поліморфний запит найшвидший | База не гарантує, що в картки є маска — лише код |
| Один `INSERT` на платіж | Таблиця «розростається» з кожним новим типом |

**Чому не можна `nullable = false` на `card_mask`:** тоді `INSERT` SEPA-платежу впаде — у нього немає маски картки, а колонка вимагає значення.

# Частина 4. JOINED — таблиця на кожен клас

```java
@Entity
@Table(name = "payments")
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class Payment extends BaseEntity { ... }

@Entity
@Table(name = "card_payments")
@PrimaryKeyJoinColumn(name = "payment_id")
public class CardPayment extends Payment {
    @Column(name = "card_mask", nullable = false, length = 19)   // тут можна NOT NULL
    private String cardMask;
}
```

Результат:

```
payments                                card_payments
id │ amount │ currency │ ...            payment_id │ card_mask           │ merchant
───┼────────┼──────────┼────            ───────────┼─────────────────────┼─────────
 1 │ 450    │ UAH      │ ...      ◀────          1 │ 4441 **** **** 1234 │ Silpo
 2 │ 1200   │ EUR      │ ...      ◀──┐
                                      │ sepa_payments
                                      │ payment_id │ beneficiary_iban │ ...
                                      └──        2 │ DE89...          │ ...
```

`@PrimaryKeyJoinColumn(name = "payment_id")` — первинний ключ таблиці нащадка, який **водночас** є зовнішнім ключем на `payments.id`. Один платіж = рядок у `payments` + рядок у таблиці нащадка з тим самим id.

| Плюси | Мінуси |
|---|---|
| Нормалізована схема, `NOT NULL` на полях нащадків | Завантаження `CardPayment` — JOIN двох таблиць |
| Новий тип — нова таблиця, старі не змінюються | Поліморфний запит — LEFT JOIN **усіх** таблиць нащадків |
| | `INSERT` нащадка — **два** `INSERT` |

# Частина 5. Як обирати

| Ситуація | Стратегія |
|---|---|
| Мало специфічних полів, часті поліморфні запити («усі платежі клієнта») | `SINGLE_TABLE` |
| Багато специфічних полів, важлива цілісність, запити переважно до конкретного типу | `JOINED` |
| Типи майже ніколи не запитують разом | Окремі entity без наслідування |

Для платежів у банку часто обирають `SINGLE_TABLE`: «історія платежів» — поліморфний запит, специфічних полів небагато. Але обидві відповіді прийнятні, якщо обґрунтовані.

**Перевір себе:**
1. Чим `@MappedSuperclass` відрізняється від `@Entity` з `@Inheritance`?
2. Скільки `INSERT` для одного `CardPayment` у `JOINED`?
3. Для чого дискримінатор у `SINGLE_TABLE`?

## Практика (25 хв)

**Важливо:** колонки полів у заготовці **уже описані** — ми вміємо це з модуля 2. Сьогодні додаємо лише анотації над класами (і чотири анотації в `BaseEntity`).

У модулі **три** persistence unit (`single-table`, `joined`, `table-per-class`) у трьох схемах бази. Кожна стратегія живе окремо, тому однакові назви таблиць не конфліктують.

### Завдання 1. BaseEntity (5 хв)

`@MappedSuperclass` над класом, `@Id` + `@GeneratedValue(strategy = GenerationType.SEQUENCE)` над `id`, `@PrePersist` над `onCreate`, `@PreUpdate` над `onUpdate`.

### Завдання 2–4. SINGLE_TABLE (8 хв)

Анотації з частини 3. Запусти `SingleTableTest`.

### Завдання 5–7. JOINED (7 хв)

Анотації з частини 4. Запусти `JoinedTest`.

### Порівняння (5 хв)

Запусти `Main` і порівняй у консолі:

| Операція | SINGLE_TABLE | JOINED |
|---|---|---|
| `persist(CardPayment)` | 1 `insert into payments` | `insert into payments` + `insert into card_payments` |
| `select p from Payment p` | 1 `select` з `payments` | `select` з `payments` + `left join card_payments` + `left join sepa_payments` |

**Експеримент (якщо є час):** у `singletable/CardPayment` додай `nullable = false` над `cardMask` і запусти `SingleTableTest`. Подивись помилку при збереженні SEPA-платежу. Поверни.

**Якщо не працює:**

| Помилка | Причина |
|---|---|
| `No identifier specified for entity` | `@Id` не на місці в `BaseEntity` або немає `@MappedSuperclass` |
| `Not an entity: CardPayment` | Немає `@Entity` над нащадком |
| `created_at` null при insert | Немає `@PrePersist` над `onCreate` |

# Частина 6. Резерв (30 хв)

## 6.1. TABLE_PER_CLASS (10 хв, завдання 8–10)

```java
@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class Payment extends BaseEntity { ... }   // таблиці немає

@Entity @Table(name = "card_payments") public class CardPayment extends Payment { ... }
@Entity @Table(name = "sepa_payments") public class SepaPayment extends Payment { ... }
```

Кожен **конкретний** клас — повна таблиця з усіма полями, включно зі спільними.

- Запит до конкретного типу — одна таблиця без JOIN.
- Поліморфний запит — `UNION ALL` усіх таблиць: повільно, незручно для індексів.
- **`IDENTITY` заборонено:** id мають бути унікальні в усій ієрархії, а в кожної таблиці своя identity-колонка. Потрібна одна спільна послідовність.

Використовують рідко.

## 6.2. Поліморфні запити і TYPE() (8 хв)

```sql
select p from Payment p                                -- усі платежі, конкретні класи
select p from Payment p where type(p) = CardPayment    -- лише карткові
select c from CardPayment c where c.merchant = 'Silpo' -- запит до нащадка напряму
```

## 6.3. Композиція замість наслідування (12 хв)

Наслідування в entity — жорстке рішення: змінити стратегію на живих даних — міграція всієї ієрархії. Альтернатива:

```java
@Entity
public class Payment {
    @Enumerated(EnumType.STRING) private PaymentMethod method;   // CARD, SEPA
    @Embedded private CardDetails card;                           // null для SEPA
    @Embedded private SepaDetails sepa;                           // null для карток
}
```

Структурно це схоже на `SINGLE_TABLE`, але без ієрархії класів.

**Коли наслідування доречне:** нащадки мають **різну поведінку**, яку зручно виразити поліморфізмом (`payment.process()` робить різне). Коли відрізняються лише поля — композиція простіша.

## Словник

| Термін | Простими словами |
|---|---|
| `@MappedSuperclass` | Батьківський клас зі спільними полями, без власної таблиці |
| Стратегія наслідування | Спосіб зберігати ієрархію класів у таблицях |
| Дискримінатор | Колонка з міткою типу рядка |
| Поліморфний запит | Запит до батьківського класу, що повертає об'єкти нащадків |
| Lifecycle callback | Метод, який Hibernate викликає в певний момент (перед INSERT тощо) |

---

## Контрольні питання

1. Чим `@MappedSuperclass` відрізняється від `@Entity` з наслідуванням?
   *Лише копіює поля в таблиці нащадків; поліморфних запитів немає.*
2. Чому в `SINGLE_TABLE` поля нащадків nullable?
   *У рядках інших типів у тій самій таблиці цих значень немає.*
3. Скільки `INSERT` для `CardPayment` у `JOINED`?
   *Два.*
4. Чому `TABLE_PER_CLASS` не працює з `IDENTITY`?
   *Id мають бути унікальні в усій ієрархії.*
5. Яку стратегію обрати для «історії всіх платежів клієнта»?
   *`SINGLE_TABLE`.*
