# Частина 1. Як зникають гроші

## 1.1. Lost update

Банк — це сотні запитів одночасно. Що, як два перекази з одного рахунку прийдуть в ту саму мить?

```
Потік A (переказ 10)                     Потік B (переказ 10)
────────────────────                     ────────────────────
SELECT balance → 1000
                                         SELECT balance → 1000
balance = 1000 - 10 = 990
UPDATE balance = 990, COMMIT
                                         balance = 1000 - 10 = 990
                                         UPDATE balance = 990, COMMIT   ← списання A перезаписане
```

Обидва перекази «успішні», з рахунку пішло 20 грн (двом отримувачам), а баланс зменшився лише на 10. Банк втратив 10 грн. Це **lost update** — «втрачене оновлення».

## 1.2. Чому база не рятує сама

На рівні **Read Committed** (за замовчуванням у PostgreSQL) кожен `UPDATE` окремо коректний. Помилка не в базі, а в шаблоні **«прочитати → порахувати в Java → записати»**. А саме так працює dirty checking: `find` → `debit()` у Java → `UPDATE` при commit.

```java
Account a = em.find(Account.class, id);   // прочитали 1000
a.debit(new BigDecimal("10"));            // порахували в Java: 990
tx.commit();                              // UPDATE accounts SET balance = 990 — без жодної перевірки
```

Два способи захисту — далі.

# Частина 2. Optimistic locking — @Version

## 2.1. Ідея

«Оптимістично» припускаємо, що конфліктів мало. Не блокуємо нічого під час читання, але **при записі перевіряємо**, чи ніхто не змінив рядок, поки ми рахували.

```java
@Entity
public class Account {
    @Version
    private Long version;      // Hibernate сам збільшує при кожному UPDATE
}
```

## 2.2. Що змінюється в SQL

```sql
-- без @Version
update accounts set balance = 990 where id = 1

-- з @Version
update accounts set balance = 990, version = 6 where id = 1 and version = 5
```

Повторюємо сценарій:

```
Потік A                                          Потік B
SELECT balance=1000, version=5
                                                 SELECT balance=1000, version=5
UPDATE ... version=6 WHERE version=5  → 1 рядок
COMMIT
                                                 UPDATE ... version=6 WHERE version=5  → 0 рядків!
                                                 → OptimisticLockException
```

Потік B не перезаписав зміни A — він отримав виняток. Його переказ треба **повторити** з актуальними даними: прочитати 990, списати 10 → 980.

Аналогія з Java: `AtomicLong.compareAndSet(expected, newValue)`, тільки на рядку бази.

## 2.3. Властивості

- Під час читання **нічого не блокується** — читання не чекають.
- Конфлікт виявляється лише при записі.
- Програш одного з потоків — нормальна ситуація: його обробляють повтором (retry) або повідомленням «дані змінилися, спробуйте ще раз».
- Поле `version` змінює **лише Hibernate**: сеттера не робимо.

# Частина 3. Pessimistic locking — SELECT FOR UPDATE

## 3.1. Ідея

«Песимістично» припускаємо, що конфлікт буде. Блокуємо рядок **уже при читанні**, до кінця транзакції.

```java
Account a = em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE);
```

```sql
select ... from accounts where id = ? for no key update
-- (Hibernate для PostgreSQL використовує "for no key update" — це блокування на запис,
--  яке не заважає вставляти рядки, що посилаються на цей рахунок)
```

## 3.2. Той самий сценарій

```
Потік A                                        Потік B
SELECT ... FOR UPDATE → 1000 (рядок заблоковано)
                                               SELECT ... FOR UPDATE → ЧЕКАЄ
UPDATE balance = 990
COMMIT (блокування знято)
                                               → отримує 990 (вже актуальне!)
                                               UPDATE balance = 980
                                               COMMIT
```

Жодних винятків і повторів: потоки просто стають у чергу.

Аналогія з Java: `synchronized` на рядку бази.

# Частина 4. Що обрати

| | Optimistic (`@Version`) | Pessimistic (`FOR UPDATE`) |
|---|---|---|
| Під час читання | Без блокувань | Рядок заблоковано |
| При конфлікті | Виняток → повтор | Очікування в черзі |
| Добре, коли | Конфлікти рідкісні | Конфлікти часті («гарячий» рахунок) |
| Ризики | Під навантаженням — лавина повторів | Deadlock; з'єднання стоять у черзі |
| Довга операція (користувач 5 хвилин редагує форму) | Єдиний варіант | Неможливо: не можна тримати блокування хвилинами |

**Для переказів у Mini Bank — pessimistic:** транзакція коротка (мілісекунди), а з одного рахунку можуть списувати багато разів одночасно. `@Version` залишаємо **теж**, як другий рубіж: він захищає від будь-якого коду, що змінює рахунок в обхід сервісу переказів.

**Перевір себе:**
1. Чому `UPDATE ... where version = 5` поверне 0 рядків?
2. Що відбувається з другим потоком при pessimistic locking?
3. Чому для редагування профілю клієнта у формі — optimistic?

## Практика (25 хв)

### Крок 0. Побачити проблему (5 хв)

Запусти тест «Демо · lost update без захисту». Він **зелений** — і це погано: 10 потоків списали по 10, а баланс 990 замість 900.

Розберіть тест разом:
- `LegacyAccount` — рахунок без жодного захисту;
- `CountDownLatch` — «зустріч потоків»: кожен потік, прочитавши баланс, чекає, доки прочитають **усі**. Так ми гарантуємо, що всі 10 прочитали 1000 до першого запису.

### Завдання 1. @Version (7 хв)

У `Account`:

```java
@Version
private Long version;

public Long getVersion() {
    return version;
}
```

Тест «1 · конфлікт версій виявляється»: два `EntityManager` читають той самий рахунок; перший комітить; другий отримує конфлікт. Баланс 900, а не 800.

У консолі: `update m09.accounts set ... version=? where id=? and version=?`.

### Завдання 2. PESSIMISTIC_WRITE (8 хв)

У `PessimisticTransferService.lock`:

```java
Account account = em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE);
```

Тест «2 · …»: 100 переказів по 10 у 10 потоках. Рахунок A — 0, рахунок B — 2000, 200 записів операцій.

У консолі: `select ... for no key update`.

### Обговорення (5 хв)

Чому в тесті pessimistic **немає** retry, а в optimistic — потрібен?

**Якщо не працює:**

| Що бачиш | Причина |
|---|---|
| Тест 2 падає з неправильним балансом | `find` без `LockModeType` |
| `ERROR: deadlock detected` | Зустрічні перекази — резерв, завдання 3 |
| Тести дуже довгі / зависають | Вбудований пул з'єднань замалий; у `persistence.xml` модуля `pool_size = 30` |

# Частина 5. Резерв (30 хв)

## 5.1. Deadlock (15 хв, завдання 3)

```
Переказ A→B                        Переказ B→A
lock A                             lock B
lock B ← чекає, доки B відпустять  lock A ← чекає, доки A відпустять
```

Кожен чекає на іншого — вічно. PostgreSQL помічає цикл і вбиває одну з транзакцій: `ERROR: deadlock detected`. Тест «3 (резерв) · зустрічні перекази» у заготовці падає саме так.

**Рішення — глобальний порядок блокувань.** Завжди блокувати рахунки за зростанням id:

```java
Long firstId = Math.min(fromId, toId);
Long secondId = Math.max(fromId, toId);
Account first = lock(em, firstId);
Account second = lock(em, secondId);
Account from = fromId.equals(firstId) ? first : second;
Account to = fromId.equals(firstId) ? second : first;
```

Тепер обидва перекази спочатку чекають на рахунок з **меншим** id — циклу немає. Той самий принцип, що й порядок `synchronized` на кількох об'єктах у Java.

## 5.2. Retry для optimistic (15 хв, ДЗ)

```java
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    TransferSupport.validate(fromId, toId, amount);
    for (int attempt = 1; ; attempt++) {
        try {
            transferOnce(fromId, toId, amount);
            return;
        } catch (RuntimeException e) {
            if (!TransferSupport.isOptimisticLockFailure(e) || attempt >= maxAttempts) {
                throw e;
            }
            backoff(attempt);
        }
    }
}
```

- Повторюємо **лише** конфлікт версій. `InsufficientFundsException` повторювати немає сенсу.
- Кожна спроба — **новий** `EntityManager`: у старому Persistence Context лежить застаріла версія.
- **Випадкова** пауза (jitter): без неї потоки зіткнуться знову в ту саму мить.
- Конфлікт може прийти як `OptimisticLockException` з `flush`, як `RollbackException` з `commit` з причиною всередині, або як `StaleStateException` Hibernate. Тому `isOptimisticLockFailure` перевіряє весь ланцюжок причин (`getCause()`).

## Словник

| Термін | Простими словами |
|---|---|
| Lost update | Паралельна транзакція перезаписала наші зміни |
| Optimistic locking | Перевірка версії при записі, без блокувань при читанні |
| `@Version` | Поле-лічильник змін рядка |
| Pessimistic locking | Блокування рядка при читанні до кінця транзакції |
| `SELECT FOR UPDATE` | SQL-запит, що блокує вибрані рядки |
| Deadlock | Дві транзакції чекають одна на одну |
| Retry | Повтор операції після конфлікту |

## Контрольні питання

1. Чому lost update не помічає база на Read Committed?
   *Кожен UPDATE коректний сам по собі; нове значення пораховано зі застарілого.*
2. Що робить Hibernate з полем `@Version` при UPDATE?
   *Додає `where version = ?` і збільшує версію; 0 рядків → `OptimisticLockException`.*
3. Коли pessimistic locking неприйнятний?
   *Коли між читанням і записом довгий проміжок (форма користувача).*
4. Як уникнути deadlock?
   *Блокувати рядки завжди в одному порядку.*
5. Чому retry потребує нового `EntityManager`?
   *Старий тримає об'єкт зі старою версією.*
