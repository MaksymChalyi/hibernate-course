## Теорія (25 хв)

### 1. Lost update (6 хв)

```
Потік A                         Потік B
read balance = 1000
                                read balance = 1000
balance = 1000 - 10 = 990
write 990, commit
                                balance = 1000 - 10 = 990
                                write 990, commit      ← списання A втрачено
```

Обидва перекази успішні, а з рахунку списано 10 замість 20. На рівні Read Committed (за замовчуванням у PostgreSQL) база цього не помічає: кожен UPDATE коректний сам по собі. Проблема в шаблоні **read → обчислити в Java → write**, а саме так працює dirty checking.

### 2. Optimistic locking: `@Version` (7 хв)

```java
@Version
private Long version;
```

Hibernate додає версію в кожен UPDATE:

```sql
update accounts set balance = 990, version = 6 where id = 1 and version = 5
```

Якщо хтось уже змінив рядок, версія в базі 6, UPDATE змінює **0 рядків**, і Hibernate кидає `OptimisticLockException` замість мовчазного перезапису.

- Блокувань під час читання немає — читання не чекають.
- Конфлікт виявляється лише при записі; програш одного з потоків — нормальна ситуація, її треба обробити (повтор або помилка користувачу).
- Поле `version` змінює лише Hibernate: сеттера немає.

Аналогія з Java: це `AtomicLong.compareAndSet(expected, new)`, тільки на рядку бази.

### 3. Pessimistic locking (7 хв)

```java
Account account = em.find(Account.class, id, LockModeType.PESSIMISTIC_WRITE);
```

```sql
select ... from accounts where id = ? for update     -- для PostgreSQL Hibernate може згенерувати "for no key update"
```

Рядок заблоковано до кінця транзакції. Інша транзакція, яка хоче заблокувати той самий рядок, **чекає**. Lost update неможливий: другий потік прочитає баланс уже після commit першого.

Аналогія з Java: `synchronized` на рядку бази.

### 4. Що обрати (5 хв)

| | Optimistic (`@Version`) | Pessimistic (`FOR UPDATE`) |
|---|---|---|
| Читання | Без блокувань | Блокує рядок |
| Конфлікт | Виняток при commit → повтор | Очікування |
| Добре, коли | Конфлікти рідкісні | Конфлікти часті («гарячий» рахунок) |
| Ризики | Багато повторів під навантаженням | Deadlock, з'єднання стоять у черзі |
| Довга операція (форма, яку користувач редагує 5 хвилин) | ✅ Єдиний варіант | ❌ Не можна тримати блокування хвилинами |

Для переказів у Mini Bank: **pessimistic** — транзакція коротка, а один рахунок може отримувати багато одночасних списань. `@Version` залишаємо як другий рубіж: він захищає від будь-якого коду, що оновлює рахунок в обхід сервісу переказів.

## Резерв (30 хв)

### Deadlock (15 хв)

```
Переказ A→B                    Переказ B→A
lock A                         lock B
lock B  ← чекає                lock A  ← чекає
```

Кожен чекає на іншого. PostgreSQL виявляє цикл і вбиває одну з транзакцій: `ERROR: deadlock detected`. Тест `oppositeTransfersDoNotDeadlock` у starter падає саме так.

Рішення — **глобальний порядок блокувань**: завжди блокувати рахунки за зростанням id.

```java
Long firstId = Math.min(fromId, toId);
Long secondId = Math.max(fromId, toId);
Account first = lock(em, firstId);
Account second = lock(em, secondId);
Account from = fromId.equals(firstId) ? first : second;
Account to = fromId.equals(firstId) ? second : first;
```

Тепер обидва перекази спочатку чекають на рахунок з меншим id — циклу немає. Це той самий принцип, що й порядок `synchronized` на кількох об'єктах у Java.

### Retry для optimistic locking (15 хв)

```java
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    for (int attempt = 1; ; attempt++) {
        try {
            transferOnce(fromId, toId, amount);   // новий EntityManager на кожну спробу
            return;
        } catch (RuntimeException e) {
            if (!isOptimisticLockFailure(e) || attempt >= maxAttempts) throw e;
            backoff(attempt);                     // випадкова пауза, що росте
        }
    }
}
```

- Повторюємо **лише конфлікт версій**. Недостатньо коштів — повтор дасть той самий результат.
- Кожна спроба — **новий `EntityManager`**: старий Persistence Context містить застарілу версію.
- Випадкова пауза (jitter): без неї потоки зіштовхуються знову в ту саму мить.
- Конфлікт може прийти як `OptimisticLockException` з `flush`, як `RollbackException` з `commit` з причиною всередині, або як `StaleStateException` Hibernate. Тому перевіряємо весь ланцюжок причин.

Це домашнє завдання; тест `optimisticTransfersWithRetrySucceed` перевіряє 25 паралельних переказів без жодної невдачі.

## Контрольні питання

1. Чому lost update не помічає база на Read Committed?
   *Кожен UPDATE коректний сам по собі; помилка в тому, що нове значення обчислено зі застарілого.*
2. Що робить Hibernate з полем `@Version` при UPDATE?
   *Додає `where version = ?` і збільшує версію; 0 змінених рядків → `OptimisticLockException`.*
3. Коли pessimistic locking неприйнятний?
   *Коли між читанням і записом довгий проміжок, наприклад редагування форми користувачем.*
4. Як уникнути deadlock при блокуванні кількох рядків?
   *Блокувати завжди в одному глобальному порядку.*
5. Чому retry потребує нового `EntityManager`?
   *Старий тримає застарілий об'єкт зі старою версією.*
